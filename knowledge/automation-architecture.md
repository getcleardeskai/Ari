# Automation Architecture — End Goal

Captured 2026-08-19. This is the actual end-state the whole project is aimed at — worth keeping
separate from the individual strategy docs since it doesn't change as often as the strategies
themselves do.

## The big picture

Two independent strategies, built and validated separately, that ultimately work together:

1. **Mean reversion** — waits for price to overextend, then trades the reversion back.
2. **Trend trading** — looks for a big directional push/move and trades with it.

They're expected to **confirm or deny each other** — e.g. trend strategy wants to go long, mean
reversion strategy is flagging "overextended, reversion likely" → conflict, sit out or reduce
size; both agree → higher-confidence trade. Exactly how they combine is TBD until both exist
independently — see "Combining the two" below.

## Build order (trader's plan, adopted as-is)

For **each** strategy, independently:
1. Break the discretionary method down into explicit, codeable rules.
2. Implement in Pine Script.
3. Backtest it, look at the stats.
4. Adjust rules/parameters based on what the stats show.
5. Repeat until it's solid on its own.

Only **after both** strategies are independently validated do we tackle combining them. Building
them together from the start was explicitly rejected as too complex given both are brand new,
not-yet-formalized methods.

## Combining the two (open problem, not yet solved)

The trader flagged this as a real unknown: the two strategies may run on **different charts /
different timeframes / different indicator sets**, so "combine them" isn't as simple as one Pine
script with two conditions ANDed together. Options to consider once we get there (not decided
yet):
- Run both as separate Pine scripts, each emitting its own signal, and reconcile them in the
  execution layer (see below) rather than inside Pine itself.
- If both end up needing multi-timeframe data anyway (very possible, both HTF bias + LTF entry
  patterns), it may be possible to pull both into one script via `request.security`, the way
  `trend-bias-qqe-strategy.pine` already pulls Daily/Weekly/Hourly bias into one place.
- Worth revisiting once each strategy's actual indicator/timeframe requirements are known —
  premature to design the merge mechanism now.

## The execution layer — what the "AI bot" actually does

This is the important part to get right conceptually: **the AI does not make trading decisions.**
The trading logic — the buy/sell signals — are fully pre-defined and pre-recorded by the Pine
Script strategies built above. The bot's job at execution time is narrow and mechanical:

1. Watch for a signal that was already generated by the (already-backtested, already-validated)
   rule set.
2. **Confirm the rule conditions are actually valid** at that moment (sanity-check, not
   re-deciding).
3. **Buy/sell immediately on candle close** based on that pre-recorded signal.

In other words: all the "intelligence" lives in the strategy design and backtesting phase, done
ahead of time by us. The live execution bot is a dumb, fast, reliable order-placer that trusts the
signal and acts on candle close — not a discretionary decision-maker in the moment. This matters
because it keeps the system's behavior fully explainable and backtestable: whatever the bot does
live should be reproducible from the same rules in a backtest.

## What this means for how we build

- Every strategy needs to end up as **explicit, deterministic rules** — no "AI, use your
  judgment" steps in the live path. Judgment/discretion is allowed during the *design* phase
  (this conversation), not the *execution* phase.
- Pine Script is the backtesting/validation tool; the actual live execution bot is a separate
  piece of infrastructure (not built yet, not blocking strategy development) that consumes
  whatever signal format the validated Pine scripts settle on.
- No re-entries, no repainting — already established as requirements in
  `pinescript/trend-bias-qqe-strategy.pine` and directly relevant here too: a live bot trusting a
  signal needs that signal to be stable/non-repainting, or it'll act on something that "un-happens"
  a moment later.

## Execution bot — concrete architecture (2026-08-19)

Decided: bot runs on the trader's own always-on PC, exposed to TradingView's webhook servers via
a **Cloudflare Tunnel** (no port-forwarding/router changes needed). Execution broker is
**Tradovate**, via its REST API.

```
Pine strategy (bias/signal already validated) --alert()--> TradingView Alert (webhook)
    --POST--> Cloudflare Tunnel --> webhook_server.py (FastAPI, local PC)
    --if secret valid & not a duplicate & DRY_RUN=false--> tradovate_client.py
    --> Tradovate REST API --> real order
```

- Both `pinescript/trend-bias-qqe-strategy.pine` and `pinescript/auto-reversion-strategy.pine`
  now fire `alert()` calls (not just `alertcondition()`) with a JSON payload
  (`secret`/`strategy`/`symbol`/`action`/`price`) on every entry AND on every exit (exit detection
  is generic — any transition from a non-flat position to flat — so it covers stop-outs,
  take-profits, and rule-based closes uniformly without the bot needing to know which one fired).
- `bot/webhook_server.py` validates the shared secret, de-dupes redelivered alerts, and — only if
  `DRY_RUN=false` — calls into `bot/tradovate_client.py` to place the order.
- Safety defaults: `DRY_RUN=true` and `TRADOVATE_ENV=demo` out of the box. Both need to be
  deliberately changed, not just left on by accident. See `bot/README.md` for the staged
  go-live process.
- Not yet built (see `bot/README.md` "What's NOT built yet"): position-size verification against
  Tradovate before ordering, contract symbol/rollover handling, daily loss limits/kill switch, and
  the actual cross-strategy combination logic (both strategies currently fire independently).
